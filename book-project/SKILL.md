# Book Project｜非虛構書籍的完整創作流程

把「一個人想寫一本書」變成可執行、可交接、可出版的專案。

這套流程已經真的走過一次（案例：家族記憶主題《把家人聚回來》——序章＋14 章＋結語、48 幅插畫規劃、讀者意見調查、驗證網站）。第一次走完得到的最重要結論是：**書的品質不是靠寫得快，而是靠「素材來源清楚、缺口誠實標示、作者終審」這三件事**。

## 三條不可違反的鐵則

1. **不編造**。作者沒提供的經驗、場景、對話、數據與專業結論，一律不寫。資料不足時**標示缺口**（「綜合示例」「待授權」「待查證」），不要用想像填滿。讀者會相信細節，捏造的細節會讓整本書失去可信度。
2. **真實與決定權在作者**。AI 負責追問、分類、起草、檢查、抓矛盾；只有作者與受訪者能確認經驗、情感與公開界線。AI 永遠不替作者決定「這段可以公開」。
3. **不擴大、不恐嚇**。不把單一家庭、單一地區、單一宗教的做法寫成全體通則；不用「不做會招厄運」「這樣才孝順」製造壓力或罪惡感。

## 開工第一件事：先問清楚，不要急著列目錄

新書專案最常見的失敗是「太早開始寫」。先花 3–6 次訪談把三件事問清楚：

- **為什麼非寫不可**：個人起點、一個最鮮明的畫面、一次明顯感到失去或轉變的時刻、希望讀者讀完做什麼。
- **誰會買**：讀者畫像（至少三種）＋「他在什麼情況下會需要這本書」。
- **邊界在哪**：不寫什麼、哪些內容需要授權、哪些家人的事不能公開。

若使用者只丟一句話（「我想寫一本關於 X 的書」）就想動工，先跑訪談，再談企劃與目錄。

## PWPM 四階段

| 階段 | 主要產出 | 完成條件（摘要） |
|---|---|---|
| **P1 Planning** | 作者訪談紀錄、出書企劃、章節企劃卡、讀者驗證計畫 | 一句話提案清楚；核心讀者與痛點清楚；核心方法成立；每章任務與範圍寫定 |
| **W Writing** | 素材台帳、逐章初稿、補訪與授權、統稿版 | 每章至少一個可核實素材或**明確標示的**示例；家族／外部事實已確認；授權處理完 |
| **P2 Publication** | 提案包、編輯校對與設計檔 | 出版方式、合約、授權範圍、印製檔完成 |
| **M Marketing** | 上市節點、讀者實作成果、IP 延伸 | 內容可長尾經營（依節慶／議題年度更新），不依賴上市期 |

## P1｜Planning

1. **作者深度訪談**（每次 30–60 分鐘，一次一個主題）。必問：最鮮明的相聚畫面／感到分散的時刻／已消失或改變的食物、分工、儀式／那位把大家牽在一起的人／希望下一代記得什麼／希望讀者立刻做什麼。每次訪談後留下逐字稿、摘要、待查項目與授權狀態。
2. **出書企劃**：一句話提案、核心命題、書名與 2–3 組副標方向、讀者畫像、痛點與價值、市場定位與競品、出版目的（文化／讀者／作者／商業）、IP 延伸方向。
3. **章節企劃卡**（＝**寫作合約**）：每章固定八格——章節任務、開場故事、核心觀點、內容範圍、案例或代表素材、一項主要實作工具、讀者「今晚就能做」的行動、待補素材與專業審讀需求。全書節奏建議固定為「家庭場景 → 讀者痛點 → 文化／關係解釋 → 方法與案例 → 本章行動」。
4. **讀者需求驗證**：訪談目標人數（案例為 24 人、三種畫像各 8）、副標與內容承諾測試、一頁式介紹頁、候補名單；**先完成招募管道整理表並逐一核實**（成員數、活躍度、版規都要標來源或「需登入」）。
5. **市場與專業查核**：至少讀 10 本直接或鄰近競品；人口／家庭／產業數據都回到原始來源與年份；地方習俗的用語與年代差異要找專業者確認。

## W｜Writing

1. **素材台帳優先**：每一項素材都要有編號、來源、日期地點、可用章節、事實狀態、授權狀態、匿名需求、原始檔位置。台帳同時是「章節資料缺口對照表」。
2. **先寫素材最成熟的章節**，不要按章號順序寫。第一輪應先建立「作者的聲音」與示範章，再往工具型、協商型、觀點型章節擴張。
3. **單章九步**：讀企劃卡 → 盤點素材與缺口 → 決定開場性質（真實／授權案例／**明確標示的**綜合示例）→ 寫初稿 → 檢查有沒有把推測寫成事實 → 加一項工具或行動 → 檔首註明初稿限制 → 更新缺口清單 → 作者確認聲音與公開界線。
4. **AI 與作者分工**：經驗與觀點由作者提供、AI 追問整理；事實由作者確認、AI 建待查清單；寫作 AI 起草、作者確認聲音；案例由作者邀請與取得同意、AI 設計題綱與匿名化建議；最終決策永遠是作者。
5. **第二輪統稿按風險與依賴排，不按章號**：補真實素材 → 取得授權 → 事實查核 → 工具實測 → 專業審讀 → 全書統稿（聲音、名詞、案例標示、長度、重複）→ 敏感度閱讀 → 作者終審。

## P2｜Publication

提案包＝一頁式簡介＋完整企劃＋作者介紹（為何非寫不可）＋讀者與競品差異＋完整目錄與每章摘要＋2–3 章代表試讀＋預估字數與時程＋平台與通路構想＋工具附件示意。

編輯流程：出版社評估簽約 → 確認書名規格與交稿日 → **結構編輯**（章序、讀者旅程、重複）→ 文字編輯 → 事實查核與引註 → 法律／隱私／照片／案例授權確認 → 工具表與插圖 → 封面與內頁 → 三校與作者清樣 → 紙本／電子／有聲同步。

視覺與產品原則：封面傳達主題而不被單一符號限制；表格與工具必須能影印、書寫或下載；長輩使用的字級與操作說明要清楚。

## M｜Marketing

年度內容節點（依主題選定，例如：春節／清明／中元／重陽）＋上市前（經授權的讀者故事、免費工具、名單）＋上市期（用真實起點與工具示範溝通，而非抽象道德）＋上市後（讀者實作成果 → 文章／短影音／Podcast → 發展工作本、工作坊、機構教材）。

## 專案基礎建設（跨 Agent／跨電腦）

新書一開始就把三層同步建起來，否則半年後接手的人（或未來的你）會從零開始：

| 層級 | 內容 | 時機 |
|---|---|---|
| L1 本地 | `AGENTS.md`（藍圖：目標、路線圖 checklist、資料夾結構、工作約定、隱私規則）＋ `handoff.md`（交接：目前做到哪、狀態、下一步、注意事項、最後更新者與電腦名） | 每個 session 讀；收工寫 |
| L2 GitHub | 私有 repo；一個 commit 對應一個清楚成果；push 後自動部署（若有網站） | 收工或指定時 |
| L3 筆記 | `專案工作流程.md`（決策紀錄、踩坑筆記、最近更動紀錄） | 有需要才讀；收工寫 |

- 檔案結構、frontmatter 最低規格、狀態機與 Git 節奏見 `references/04-工具鏈與陷阱.md`。
- 若專案已有 `startup`／`shutdown`／`project-init` 技能，直接搭配使用（開工讀、收工寫、初始化建三層）。

## 驗證網站與繁簡切換（摘要）

驗證規模超過 30 人或需要長期收集時才做網站；先確認流程再做。最低功能與技術慣例見 `references/04-工具鏈與陷阱.md`。

- **繁／簡不要維護兩份內容**：用 `opencc-js` 轉換，cookie 記偏好（`zh-Hant`／`zh-Hans`）；後台與使用者原話不轉。
- **表單頁（問卷）**：伺服器產生兩份題目，頁內切換；只靠 DOM 轉換會被 React 重新渲染蓋回。
- **版頭與頁面文案**：由全站層轉換，表單容器加 `data-lang-skip`，切換時發事件同步。
- **招募管道表**：先列名單與核實狀態（成員數、活躍度、版規），再開始收案；格式見 `references/03-驗證出版與行銷.md`。

## 內容工具鏈（摘要）

- **Markdown 是正本**，docx／PDF 只是寄送與備份副本。任何轉檔工具都從 Markdown 產生，不要反向編輯。
- 書稿、企劃、台帳全部放同一個專案資料夾（Obsidian vault 內），用 frontmatter 標狀態與階段。
- 錄音、照片、逐字稿、含個資的授權文件**不進 repo**；repo 只記代碼、授權狀態與安全位置。
- 詳細指令、轉檔實作與已知陷阱（雲端硬碟不能直接 npm，Word 轉 PDF 會卡死的工作區，PowerShell 中文與行尾，台語 ASR 誤辨，無視覺模型怎麼審圖）見 `references/04-工具鏈與陷阱.md`。

## 一頁版檢查表（每次交付前掃一眼）

每章：開場來源清楚？示例有標示？人名地名年代親屬已確認或標待查？地方習俗沒被當通則？沒有用恐懼或孝道施壓？不同信仰／性別／世代被尊重？敏感內容遵守自願揭露？授權狀態清楚？只有一個主要行動？與他章沒有大量重複？

全書：企劃／目錄／章號／章名／雙向連結一致？核心方法在全書都有落點？真實故事與工具內容比例平衡？引用與數據可追溯？可辨識資訊已取得同意或妥善匿名？作者逐章確認聲音與公開界線？專業審讀意見已記錄採納或不採納理由？

網站（若有）：招募管道表已核實？繁／簡雙向切換正常且不清除答案？後台與使用者原話不被轉換？同意書版本與程式一致？上線後健康檢查通過？
