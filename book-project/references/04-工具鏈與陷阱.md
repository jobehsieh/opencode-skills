# 04 工具鏈與陷阱

這一節是「實際動手時會踩到的東西」。多數是 Windows＋雲端硬碟＋中文環境的實測結果。

## 一、專案結構

```
創作庫/<書名>/
├─ AGENTS.md                    # 藍圖（目標、路線圖、結構、約定、隱私規則）
├─ handoff.md                   # 交接（目前做到哪、狀態、下一步、注意事項）
├─ 專案工作流程.md               # 詳細筆記（決策、踩坑、更動紀錄）
├─ <書名>｜出書企劃.md
├─ <書名>｜章節企劃卡.md
├─ <書名>｜完整出書流程.md
├─ 序章｜…｜初稿.md
├─ 第一章｜…｜初稿.md … 第N章
├─ 結語｜…｜初稿.md
├─ 家族補訪包/ 或 訪談素材/      # 題綱、邀請文字、授權表、素材台帳
├─ 讀者驗證包/                  # 同意書、問卷、實測表、招募文案
├─ 插畫資產/ 或 視覺素材/
└─ <網站專案>/                  # 需要線上收集時才有
```

**repo 只放 Markdown 與少量必要資產**。錄音、照片、逐字稿、含個資的授權文件都放受控位置，repo 只記代碼與位置。

## 二、frontmatter 與狀態

最低規格：

```yaml
---
title: 文件標題
type: book-manuscript      # book-manuscript / book-plan / material-ledger / consent-template …
book: <書名>
chapter: 1
status: first-draft
stage: Writing
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: [<書名>, 章節初稿]
---
```

建議狀態機（一次只前進一格）：
`idea` → `interviewing` → `first-draft` → `author-review` → `fact-check` → `expert-review` → `revised-draft` → `copyedit` → `final`

## 三、Git 節奏與三層同步

- 一個 commit 對應一個**清楚成果**（「完成第一輪初稿」「補入家族訪談案例」），不要拆成幾十個碎 commit，也不要把多件事混在一起。
- 提交前檢查 `git diff`、敏感資訊、未授權的照片與錄音。
- commit 訊息寫「動詞＋對象」，正文列 3–5 條「改了什麼＋為什麼」。不要寫「更新」「修改」。
- 收工時更新 `handoff.md` 的進度、下一步、阻礙與 commit 編號。
- 三層同步（本地／GitHub／筆記）用 `startup`、`shutdown`、`project-init` 技能即可；**換電腦時要確認全域技能與本機工具不在 repo 裡**（例如 ASR 模型、MCP 設定）。

## 四、Markdown → docx

環境通常沒有 pandoc／LibreOffice，用 **python-docx 自寫轉換器**最穩。規格：

- 頁面與字體：依既有慣例（例如 Letter 或 A4、左右邊界、**微軟正黑體 11pt**）。
- 標題：`#`/`##`/`###` 對應 Heading 1/2/3。
- 清單：`- ` 用 List Bullet；**勾選框 `- [ ]` 轉成 `☐`**（`- [x]` → `☑`）。
- 表格：Table Grid；**欄位超過 8 個改橫式**。
- 引用：`>` 轉成一般段落（可加縮排）。
- `[[wikilink]]` 轉純文字；去掉 frontmatter。
- **`List Number` 樣式會在同一份文件內連續編號**（跨清單不會重新從 1 開始）→ 改用內文寫「1. 」加懸掛縮排。
- 行內 `**粗體**` 要保留成真粗體；轉完檢查有沒有殘留 `**`、`` ` ``、`[[`。

轉完務必**產出 PDF 並目視**（本機若無視覺能力，就把 PDF 交給使用者看，或抽文字比對關鍵字）。

## 五、docx → PDF

- 有 LibreOffice 用 `soffice --headless --convert-to pdf`。
- 只有 Microsoft Word 時，可用不可見的 Word COM 匯出。**但實測在部分環境會無限卡住**（`ExportAsFixedFormat`、`ComputeStatistics` 都可能無回應，對雲端硬碟路徑與本機路徑都一樣），此時最務實的做法是**請使用者用 Word 手動另存 PDF**（用 `Start-Process` 直接把檔案在 Word 開起來給他）。
- 卡片式工具（要寄給專業者審閱的同意書等）最好同時保留 `.docx`（可編輯）與 `.pdf`（固定版），並在 README 註明「來源更新後要重新轉製」。

## 六、PDF 抽字與驗證

- 用 **PyMuPDF（`import fitz`）** 抽文字，比 OCR 快且準；文字型 PDF（Word 產出）效果最好。
- 驗證方式：抽文字後檢查關鍵字是否存在、不該出現的字串是否已消失、頁數是否合理。這比「看起來沒問題」可靠。

## 七、雲端硬碟（Google Drive / OneDrive）陷阱

- **不要在雲端硬碟資料夾內 `npm ci` 或安裝大量檔案**：會產生大量 0 位元檔案，工具鏈直接壞掉。
- 正確做法：用 `robocopy` 把原始碼同步到**本機磁碟**的副本，在副本跑安裝與測試；寫一個 `local-run.ps1`（同步 → 必要時安裝 → 執行）把這件事固定成一行指令。
- Word／Excel 開著檔案時，其他程式讀取會失敗（被鎖）。移動檔案前先關掉 Office。
- `robocopy /MIR` 才能在目標端同步「已從來源移走的檔案」（只 `/E` 會殘留舊檔）。

## 八、PowerShell 5.1 陷阱（Windows）

- 主控台輸出中文會變亂碼：**不要靠主控台判讀內容**，把輸出寫進 UTF-8 檔再讀。
- **無 BOM 的 UTF-8 `.ps1` 內含中文會解析失敗**：腳本一律寫成純 ASCII，或存成含 BOM 的 UTF-8。
- 不支援 `&&`；多行 commit 訊息貼在 `-m` 會斷行報錯，改用 `git commit -F <檔案>` 或多次 `-m`。
- `git push`、npm 的進度訊息走 stderr，會被顯示成錯誤，但其實成功——以 `master -> master` 與 `git status -sb` 為準。
- 用 `Start-Process` 啟動專案 `.ps1` 會被 ExecutionPolicy 擋下，需加 `-ExecutionPolicy Bypass`。
- 行尾：專案若混用 CRLF/LF，用 `git config core.autocrlf true`，編輯後可把單一檔案正規化回原本格式（並保留 BOM 狀態）。

## 九、台語／方言語音轉逐字稿

- 開源 ASR 對台語可用（例如 Breeze 系列），但**人名、地名、寺名、稱謂幾乎不可信**，且常分不清夫家／娘家一類歸屬。
- ASR 稿只當線索；**事實一律請本人校訂**，校訂版優先於任何 ASR 判讀。
- 文字型 PDF 的校訂稿可直接用 PyMuPDF 抽字，不需 OCR。

## 十、沒有視覺能力時怎麼審圖

- 把多張縮圖拼成 contact sheet，交給有視覺能力的模型逐格描述（主題、有沒有可讀文字）。
- 或直接把圖交給使用者目視，並**明確列出要他確認的項目**（中文是否正常、勾選框是否顯示成 ☐、表格有沒有跑掉）。
- 不要用「應該沒問題」帶過需要目視的排版。

## 十一、網站化驗證平台（需要時才做）

技術選擇：Next.js（App Router）＋MongoDB Atlas 免費層＋Vercel Hobby。關鍵慣例：

- **資料庫一律走 migration**：新集合／驗證器／索引都寫在 `migrations/NNN-*.ts`，並註冊到索引檔；**migration 一旦套用就不能改內容**（有 checksum），要改就新增一筆。
- **題目與設定放程式內設定檔**（問卷定義、驗證項目定義），後台只顯示唯讀內容；改題目要升版本字串。
- **匿名匯出採白名單**：匯出欄位明確列出，並用測試確保不會夾帶姓名、Email、電話。
- **同意書版本治理**：改條文＝升版本＋新內容雜湊＋寫入資料庫新文件；舊文件不得原地修改。
- 環境變數：既有環境變數**優先**於 `--env-file`，所以要指向測試庫時，先設環境變數再跑指令。
- 部署：`git push` 觸發自動部署，但**migration 不會自動跑**，要手動執行；上線後的第一件事是打健康檢查端點。
- 收真實資料前必須確認：「這個環境指向哪一個資料庫」——用一次測試寫入＋查詢反證，不要靠推測。
- G:／雲端硬碟上的 repo 一樣用「本機副本 + local-run 腳本」模式。

## 十二、專案儀表板（開工／收工）

- 開工：讀 `AGENTS.md`＋`handoff.md`、看 `git status`／fetch 落後幾個 commit、確認上次是否在另一台電腦收工。
- 收工：更新 `AGENTS.md` 進度、整份改寫 `handoff.md`（含更新者與電腦名、push 狀態）、把決策與踩坑寫進 `專案工作流程.md`、commit＋push。
- 這兩件事有現成技能（`startup`／`shutdown`）就直接用；沒有就用上面的清單手動做。**沒有交接檔的專案，三個月後等於重新開始。**

## 十三、繁體／簡體切換（讀者面向網站）

華文書的讀者可能來自台灣、香港、東南亞與大陸。若網站要給簡體讀者使用，**不要維護兩份內容**，用轉換層：

- **套件**：`opencc-js`。只做繁→簡時用 `opencc-js/t2cn`（約 107KB），不要載入 full（1MB+）。伺服器端可用 full。
- **偏好存放**：cookie（例如 `btfb_lang`／`ldh_lang`，一年），值用 `zh-Hant`／`zh-Hans`；同時支援 `?lang=` 覆寫。
- **全站層**：在 root layout 包一個 client `LanguageProvider`，讀 cookie 後轉換 DOM 文字節點與 `placeholder/title/aria-label/alt`，並用 `MutationObserver` 處理動態內容；`document.title` 也要轉。
- **不要轉換**：`/admin/*`（作者後台維持繁體）、`input/textarea` 的值（使用者的原話）、使用者填答的顯示區（加 `data-lang-skip`）。
- **問卷這類大型 client form 要特別處理**：只靠 DOM 轉換，React 重新渲染會把文字畫回繁體。正解是**伺服器一次產生繁／簡兩份題目**，表單內建切換；切換只改 state，不清除已填答案。
- **頁面文案與版頭**：表單以外的伺服器文案交給全站轉換；表單容器加 `data-lang-skip`，並用 `window.dispatchEvent(new CustomEvent("…-lang"))` 通知全站層同步版頭與標題。
- **避免閃爍**：在 hydration 後、繪製前轉換（isomorphic `useLayoutEffect`）；若要完全零閃爍，必須改成伺服器依 cookie 輸出兩種 HTML，工程較大，先確認是否值得。
- **驗收**：雙向切換（繁→簡→繁）、重新載入保留、cookie 正確、後台不受影響、使用者答案不被轉換、表單切換後答案還在。
- **已知限制**：專有名詞可能被轉成慣用簡體（例如「著作」→「着作」），必要時加白名單；`useLayoutEffect` 在慢網路仍可能短暫看到繁體。
