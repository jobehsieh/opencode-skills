# 需求規格卡模板

Phase 5 依此模板生成。**硬限制：一個螢幕讀完**（約 40 行內）——超過就失去「掃一眼確認」的價值，那是這張卡存在的唯一理由。

存檔位置：`<專案>/rdq/RDQ-spec-<任務slug>-<YYYYMMDD>.md`
不在專案資料夾時：先只貼對話，問過使用者才落檔。

---

## 逐字模板

```markdown
---
rdq_version: 1
task: <一句話任務，≤30 字>
domain: <workshop|slides|lesson|video|dev|general>
date: <YYYY-MM-DD>
status: draft          # draft → confirmed（唯一閘門，未 confirmed 不得執行）
telemetry:
  mode: <lite|full>
  rounds: <訪談輪數>
  questions: <總題數>
  q4_adopted: <Ⅳ 菜單採納條數>
  revisions: 0         # 確認後每次修改 +1
downstream: <交棒的技能名稱，或 self>
---

# RDQ 需求規格：<任務名>

## 一句話任務
<把整件事濃縮成一句，這句要能單獨看懂>

## ✅ 已確認
- <需求>（Ⅰ）
- <需求>（Ⅲ）
<每條尾註來源象限：Ⅰ＝使用者明說或環境掃描、Ⅱ＝解答後確立、Ⅲ＝訪談挖出>

## ❓ 假設（未確認，已採預設值，隨時可推翻）
- <假設>→ 預設採 <值>
<所有黃燈推測與跳過的問題都列在這裡。這是本卡的核心：把「沒問到的」顯性化，
 讓使用者用「掃一眼、推翻不對的」取代「逐題回答」>

## ➕ 已採納（象限Ⅳ）
- <建議>

## ❌ 排除項（明確不做）
- <未採納的建議或已告知但選擇不處理的風險>
<明確決定不做什麼也是需求。防止下游技能自作主張加回來，日後出事也有據可查>

## 📋 一段式需求規格
<一段完整散文，仿方法論第十節示例。這段是交棒下游技能的唯一載體——
 任何技能不需要理解 RDQ 也能直接把這段當輸入。關鍵詞（人名/日期/數字/檔名）用粗體>

- [ ] <做完後對照用，2–4 條>
```

## 欄位說明

### `status` 閘門

| 值 | 意義 |
|---|---|
| `draft` | 訪談完成、**尚未確認**。任何 model／session／Agent 讀到都應停下要求確認，**不得執行** |
| `confirmed` | 使用者已確認。可以動工，可以交棒 |

把「使用者確認」從口頭流程變成**機器可查的狀態**——跨 session、跨 Agent、換 model 都不會誤執行未確認的需求。這是方法論第六步硬停點的工程化。

### `telemetry`

五個欄位，全部是**訪談當下就已知的數字**，填寫成本近零。唯一需要事後維護的是 `revisions`：使用者每要求一次修改就 +1。

**定位務必誠實**：這是**單臂描述性資料**，不是對照實驗證據。沒有對照組，而且使用者選擇跳過 RDQ 的任務系統性地偏簡單，直接比較會被任務難度混淆。日後真要做對照實驗，需另行設計配對任務。

### 各段落的功能

| 段落 | 它在解決什麼 |
|---|---|
| ✅ 已確認 | 讓使用者看見「我理解對了嗎」 |
| ❓ 假設 | **確認成本的轉移機制**——七步能壓成 2–3 次互動的關鍵 |
| ➕ 採納 | 象限Ⅳ 的裁決結果 |
| ❌ 排除 | 防範圍蔓延、防下游自作主張 |
| 📋 一段式規格 | 交棒介面（下游技能唯一需要讀的東西） |
| ✔ 驗收條件 | 執行完的自我檢查 |

## 寫作要求

- **繁體中文**，用詞貼近台灣教學現場
- 關鍵詞（人名、日期、數字、檔名、路徑）一律**粗體**——語音輸入同音錯字的最後一道安全網
- 假設清單寧可多列，**沒問到的一律列出來**；漏列比多列危險
- 一段式規格要能獨立看懂，不可出現「如上所述」「同前」這種依賴上文的寫法
- 空段落直接省略（日常模式）；示範模式才保留佔位行
